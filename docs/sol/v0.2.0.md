# SOL Engine v0.2.0 — story foundation

Status: active development

## Objective

Establish the save-persistent runtime contract for SOL story systems before map-specific narrative content is authored.

## Story contract 1

- Stable numeric IDs use the inclusive range 1–65535.
- Events, objectives, subtitles, and radio cues are separate typed namespaces.
- `SolStoryState` is an undroppable inventory object so ordinary member state follows the player through save serialization.
- Recorded events, completed objectives, seen subtitles, heard radio cues, and the current objective are stored explicitly.
- Duplicate runtime records are ignored by the state API.
- Contract version is stored with the state so future migrations can distinguish save formats.
- `SolBootstrap` guarantees each active player owns exactly one story-state item on world load, player entry, and player spawn.
- The bootstrap uses UZDoom's native `FindInventory`/`GiveInventoryType` path, so old saves missing the v0.2.0 state object are upgraded when the player becomes available without duplicating an existing state object.

The first foundation cycle intentionally contains no authored E1M1 objective, subtitle, or radio text. Those IDs and strings are owned by the sibling editor story manifest and will be added as map content is designed.

## Compatibility

`sol.pk3` remains bundle contract 1 and wadpack contract 2. The runtime component remains entry 19; its version advances to v0.2.0 while the eighteen-resource presentation stack is unchanged.

## Validation

CI checks the story entry-point includes, ID bounds, persistent state fields, deterministic player-state attachment hooks, runtime package contents, and the existing classic Doom progression/package contracts. The lifecycle hook signatures and inventory lookup/give APIs were also checked against the UZDoom ZScript sources used by this fork.
